 8. [mostly done] improvements/08-rvsc1-embench-miscompiles.md
    Root cause found and fixed in gcc 0b3abf309dd; 4 of the 5 failures resolved,
    qrduino still open.

    The absolute-address sequences replacing auipc-relative jumps and calls
    hardcode t0 in raw asm text -- the jump, six ordered-comparison/branch-NE
    forms, indirect jump, tablejump and both call sequences -- and none declares
    the clobber in RTL. t1 was already reserved as fixed in
    riscv_conditional_register_usage for exactly this reason, but when
    2666f97a4cb moved the jump synthesis t1 -> t0 to avoid the call-address
    temporary, the reservation did not follow. Every plain jump could therefore
    destroy a live t0. Reserving t0 fixes the whole family in one place rather
    than pattern by pattern; it costs one allocatable register on sc0/sc1.

    Found by reducing edn to a standalone jpegdct (about 40 lines), then reading
    the spike --log-commits trace backwards: t0 held an array offset across a
    loop back edge, the jump overwrote it with its own target, `sw t0,40(sp)`
    spilled that, and the reload became a wild pointer.

    nsichneu's "timeout" was the same defect, not slowness -- it now retires
    14682354 against 14689559 before the defect. Two benchmarks that had been
    passing were also doing wasted work: aha-mont64 413815964 -> 197361701 and
    depthconv 1212764378 -> 593772817, both roughly halving. So the corruption
    was inflating results even where nothing crashed.

    Verified: ISA 95/95, behavioral 30/30, torture static sweep 8150/8150 clean,
    0 ICEs, 0 violations. Both Embench tables re-measured and main.typ updated:
    static geomean unchanged at x7.13 (15 rows moved under 0.4% from the lost
    register), dynamic geomean x15.5 over 14 -> x12.6 over 17, and the prose that
    described four crashes and a timeout now describes the fix. Table captions
    cite 0b3abf309dd.

    Still open: qrduino fails its output check at -O2/-O3 (passes -O0/-O1/-Os,
    passes under rvsc2). Established so far: it is the memcmp that fails, not the
    heap check; the first wrong byte is index 1 of 22; it survives -fno-inline,
    -fno-schedule-insns2, -fno-reorder-blocks, -fno-gcse, -fno-tree-vectorize,
    -fno-ipa-cp, -fno-strict-aliasing; no single -m flag fixes it; and compiling
    any one TU at -O1 -- even support/main.c, which cannot touch the encoder's
    arithmetic -- makes it pass, so it looks layout- or allocation-sensitive.
    Also noted: -mbyte and -mandi fail to build at all, worth a separate look.

 9. improvements/09-cost-table-dynamic-counts-stale.md   [NEW -- found by item 6]
    Every row of @tab-synthesis-cost whose expansion contains a loop is
    understated 2-4x. Measured at HEAD by differencing one-call against
    two-call programs on Spike: sb 295 (table ~100), sh ~200 (~105), lb/lbu
    321 (~80), lh/lhu 340/337 (~80); a hand-count of test_sh (216) corroborates
    the dynamic figure. Probable cause is the !TARGET_AUIPC back edge, 3
    instructions (lui/addi/jr) where a plain j is 1, paid every iteration of
    every synthesis loop. The offset scan also shows stores and loads have
    opposite worst cases -- a load is worst when *aligned*, because the SRL
    extraction loop gets cheaper as the shift grows (shr1=159 vs shr31=39) --
    so the table cannot be spot-checked at a single offset. Remaining looping
    rows (sll/srl/sra var, slt, sltu, blt, bge, rvsc0 lui) unmeasured and
    presumed equally stale; the straight-line rows are fine. rvsc0 needs
    analytic counting instead of differencing, since with no jalr there is no
    call to difference.

10. improvements/10-libgcc-asm-violates-sc1-isa.md   [NEW -- found by item 8]
    libgcc.a contains instructions sc1 does not implement: muldi3.o and div.o
    carry native srli/slli. They come from upstream's hand-written
    libgcc/config/riscv/div.S and muldi3.S, and -mno-shift is a compiler flag
    with no effect on .S sources, so synthesis is bypassed entirely. Any sc1
    program using * / or % links them.

    Invisible from both directions at once, which is why it survived: main.py
    and torture_isa.py disassemble compiler-produced objects and never look at
    libgcc.a, while the behavioral tests run under spike --isa=rv32imac..., what
    pk needs, so the forbidden instructions execute happily instead of trapping.

    Affects no measurement in the thesis -- Spike runs them, so every behavioral
    and Embench result stands -- but it does dent the pedagogical claim: on real
    sc1 hardware a program using division would hit an illegal instruction.
    Fix is probably to drop div.S/muldi3.S from LIB1ASMFUNCS in the t-rvsc
    fragment so the generic libgcc2.c versions get compiled through the normal
    path; the shifts involved are shift-by-one, the cheapest possible synthesis.
    Worth also extending the ISA check to the linked ELF rather than to objects
    only, which would have caught this immediately and subsumes the per-object
    check.
