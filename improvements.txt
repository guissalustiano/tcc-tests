 8. [done] improvements/08-rvsc1-embench-miscompiles.md
    Two distinct backend defects, both found and fixed; all nineteen Embench
    benchmarks now execute correctly under rvsc1.

    (a) gcc 0b3abf309dd -- the absolute-address sequences replacing
    auipc-relative jumps and calls hardcode t0 in raw asm text (jump, six
    ordered-comparison/branch-NE forms, indirect jump, tablejump, both call
    sequences), none declaring the clobber in RTL. t1 was already reserved as
    fixed for exactly this reason, but when 2666f97a4cb moved the jump
    synthesis t1 -> t0 the reservation did not follow, so any plain jump could
    destroy a live t0. Fixed edn, sglib-combined, wikisort (segfaults) and
    nsichneu (a diversion, not slowness -- 14682354 retired against 14689559
    before the defect). Two benchmarks that had been passing were also doing
    wasted work: aha-mont64 413815964 -> 197361701, depthconv 1212764378 ->
    593772817. Found by reducing edn to a 40-line jpegdct and reading the
    spike --log-commits trace backwards.

    (b) gcc 8a0646efee4 -- qrduino did not share that cause. With no sb, a byte
    store becomes a read-modify-write of the enclosing word, but the RTL still
    names only the byte, and alias analysis traces the aligned address through
    the `and' with -4 to the object's own symbol. Two stores to distinct char
    globals therefore looked non-conflicting and both word loads sank above both
    word stores. initecc does `VERSION = vers; WD = 17 + 4 * vers;' on adjacent
    unsigned char globals, so the second store wrote back its stale copy of the
    first: WD correct, VERSION zero, doaligns() took its early return, and the
    QR frame came out wrong. Not a qrduino bug at all -- six lines reproduce it:
    `unsigned char A, B; void f(unsigned char v){ A=v; B=17+4*v; }' loses A at
    -O2/-O3. Fixed by routing all nine synthesized word MEMs through
    riscv_subword_container_mem (alias set 0 + MEM_VOLATILE_P). Found by
    bisecting the encoder with checksum probes: output -> fillframe ->
    initframe -> doaligns doing nothing -> VERSION reading 0 while WD read 25.

    Cost of (b): a synthesized sub-word access can no longer reuse a word its
    neighbour just loaded. Almost all of it lands on statemate, x59 -> x107
    dynamic; static geomean is unchanged at x7.13.

    Verified: ISA 95/95 (sc1) and 60/60 (sc0), behavioral 30/30 (sc1) and 45/45
    (sc0), static torture sweep 8150/8150 clean with 0 ICEs and 0 violations,
    full torture execute suite 8145/8420 with 2 failures against 36 before.
    Both remaining failures were 20030125-1.c at -O1/-Os, which upstream guards
    with dg-require-effective-target c99_runtime; this target has no C99 math
    runtime, GCC correctly declines to narrow floor -> floorf, and the test's own
    weak floor aborts. The harness parses dg-options but not
    dg-require-effective-target, so the test joins KNOWN_UNSUPPORTED with the
    other inapplicable ones, giving 8142/8420, 278 skipped, 0 failed.

    Both Embench tables re-measured and main.typ updated: dynamic geomean x12.6
    over 17 -> x13.9 over 18 (the 19th, wikisort, has no rvsc2 baseline), static
    x7.13, captions cite 8a0646efee4. The §Discussion and §Results Summary
    correctness qualifications added when the crashes were found are now

 9. improvements/09-cost-table-dynamic-counts-stale.md   [NEW -- found by item 6]
    Every row of @tab-synthesis-cost whose expansion contains a loop is
    understated 2-4x. Measured at HEAD by differencing one-call against
    two-call programs on Spike: sb 295 (table ~100), sh ~200 (~105), lb/lbu
    321 (~80), lh/lhu 340/337 (~80); a hand-count of test_sh (216) corroborates
    the dynamic figure. Probable cause is the !TARGET_AUIPC back edge, 3
    instructions (lui/addi/jr) where a plain j is 1, paid every iteration of
    every synthesis loop. The offset scan also shows stores and loads have
    opposite worst cases -- a load is worst when *aligned*, because the SRL
    extraction loop gets cheaper as the shift grows (shr1=159 vs shr31=39) --
    so the table cannot be spot-checked at a single offset. Remaining looping
    rows (sll/srl/sra var, slt, sltu, blt, bge, rvsc0 lui) unmeasured and
    presumed equally stale; the straight-line rows are fine. rvsc0 needs
    analytic counting instead of differencing, since with no jalr there is no
    call to difference.

10. [done] improvements/10-libgcc-asm-violates-sc1-isa.md
    Fixed in gcc f2e7bfaecbb. libgcc.a for rvsc0 and rvsc1 now contains zero
    shift instructions.

    The write-up's "option 1" (drop the .S files, let libgcc2.c supply the C
    versions) does not work -- libgcc2.c has no SImode divide or multiply units
    at all. The five symbols div.S and muldi3.S actually provide here are
    __divsi3, __modsi3, __udivsi3, __umodsi3 and __mulsi3, so the replacement
    (libgcc/config/riscv/divmul_rvsc.c) had to be written. It contains no right
    shifts: a constant >>1 costs ~159 instructions on these targets while <<1 is
    one add, so both routines walk bits upward. Division by zero follows the
    RISC-V spec, matching the div.S being replaced.

    Scoped to rvsc0/rvsc1 via a new t-rvsc-noshift fragment. Applying it to all
    rvsc targets -- my first attempt -- cost rvsc2 a factor of two on the
    64-bit-multiply-heavy benchmarks and pushed sc2/gcc17 from 1.004 to 1.774,
    since rvsc2 implements shifts natively and the assembly is legal there. The
    multi3_rvsc.c replacement and the blanket -O0 on libgcc2.c were moved to the
    same fragment for the same reason: both are workarounds for IRA misbehaviour
    inside synthesis loops, which only exist where the ISA lacks the instruction,
    and both had been slowing rvsc2 for nothing.

    The real trap was in include/longlong.h, not in the C. Its __muluw3 is inline
    asm calling __mulsi3 with a clobber list of only "ra","a2","a3", commented
    "We rely on the fact that MULUW3 doesn't clobber the t-registers" -- true of
    muldi3.S, not of the symbol, and unenforced. A C __mulsi3 clobbers whatever
    the allocator picks, so the asm corrupted its caller and __muldi3 returned
    wrong cross terms whenever either operand's high word was nonzero. That broke
    24 torture cases. Targets without the assembly now define __RVSC_NO_MULASM__
    and get a plain multiply; everyone else is untouched. Diagnosing it needed
    host-computed reference values -- comparing against rvsc2 was misleading,
    because its libgcc is a different build.

    Cost, and it is large: sc1 no longer benefits from instructions it cannot
    execute. Dynamic geomean goes x13.9 over 18 benchmarks to x22.2 over 19, with
    the division-heavy ones moving most (ud x1.3 -> x41.5, tarfind x5.2 -> x53.8,
    matmult-int x1.0 -> x3.6). Static geomean is unchanged at x7.13, since that
    measurement is object-level and never included libgcc. wikisort now links
    under rvsc2, so all 19 benchmarks are in the geomean.

    Verified: ISA 95/95 (sc1) and 60/60 (sc0), behavioral 30/30 and 45/45, static
    torture sweep 8145/8145 clean, full torture execute suite 8142/8420 with 0
    failures, and __mulsi3/__muldi3/divide checked against host-computed values.

11. improvements/11-linked-program-not-isa-clean.md   [NEW -- found by item 10]
    Extending the allowlist check from objects to the linked ELF shows the
    library was never the whole story: a linked sc1 program still contains auipc,
    andi, bgeu, bltu, bne, csrrw, ecall, jal, sb and slli. Two causes. First,
    middle-end libcalls -- ordinary calls correctly use lui/jalr, but a libcall
    such as the __mulsi3 reference inside _divdi3.o is emitted as a `call' pseudo
    that the assembler expands to auipc/jalr and the linker does not relax away;
    that one is this work's own defect and is the part worth fixing. Second, the
    C runtime: csrrw and ecall come from the HTIF/syscall layer and the rest from
    newlib, which is a scope question -- a bare-metal sc1 processor has no ecall
    target -- and probably wants deciding in §7 rather than fixing.

    Affects no measurement, since Spike executes all of it. It does mean "every
    object the compiler produced is ISA-clean" is true and verified, while "the
    binary runs on the processor the student built" is not yet. Suggested fix is
    a linked-ELF allowlist check in the behavioral harnesses, reported separately
    from the per-object result so the two claims stay distinguishable.
